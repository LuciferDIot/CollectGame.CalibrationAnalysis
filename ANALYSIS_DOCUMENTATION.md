## Project Overview

### Objective
Construct a derived, analysis-ready calibration dataset to characterize baseline behavioral tendencies, compare gameplay modes under controlled conditions, and support parameter calibration prior to AURA's adaptive system activation.

### Position in AURA Pipeline
```
Telemetry (30s windows)
    ↓
Calibration Dataset Construction ← [THIS PROJECT]
    ↓
Normalization
    ↓
Behavioral Clustering
    ↓
Percentages + Deltas
    ↓
ANFIS Reasoning Layer
    ↓
Real-Time Procedural Content Adaptation
```

### Guiding Principles
1. **Immutability**: Raw telemetry is never modified
2. **Derivation over Correction**: No interpolation or retroactive smoothing
3. **Temporal Alignment**: Death events are mapped, not predicted
4. **Reproducibility**: All processes can be re-executed on future datasets

## Notebook 00: Dataset Generation

**File**: `00_generate_calibration_dataset.ipynb`  
**Objective**: Construct calibration dataset by temporally aligning raw telemetry with death events

### Methodology

#### Temporal Alignment Rule
> A death event is associated with the **nearest following telemetry window** for the same user and mode.  
> Constraint: `Death Time ≤ Telemetry Window Time`

**Implementation**: `pd.merge_asof(direction='forward')`

#### Why This Approach?
1. **Telemetry timestamps mark window end**: A 30-second window ending at T=100 captures events from T=70 to T=100
2. **Death contained in window**: Death at T=85 should map to window ending at T=100, not T=70
3. **No look-back bias**: Deaths cannot influence past windows that already occurred

### Process Steps

```python
# Step 1: Load raw data
telemetry = pd.read_csv('telemetry.calibration_telemetry.csv')  # 474 rows
deaths = pd.read_csv('telemetry.deathevents.csv')  # 57 deaths
users = pd.read_csv('telemetry.users.csv')  # 8 users

# Step 2: Validate death events against registered users
invalid_deaths = deaths[~deaths['userId'].isin(users['userId'])]
# Result: 0 invalid deaths

# Step 3: Sort data for merge_asof
telemetry_sorted = telemetry.sort_values(['userId', 'modeId', 'timestamp'])
deaths_sorted = deaths.sort_values(['userId', 'modeId', 'timestamp'])

# Step 4: Temporal alignment
aligned = pd.merge_asof(
    deaths_sorted, 
    telemetry_sorted[['userId', 'modeId', 'timestamp']],
    on='timestamp',
    by=['userId', 'modeId'],
    direction='forward'  # Critical: find nearest FOLLOWING window
)

# Step 5: Aggregate deaths per window
death_counts = aligned.groupby(['userId', 'modeId', 'window_timestamp']).size()
telemetry['deathCountInWindow'] = death_counts.reindex(telemetry.index, fill_value=0)
telemetry['deathOccurredInWindow'] = (telemetry['deathCountInWindow'] > 0).astype(int)
```

### Results

**Alignment Success**: 55 of 57 deaths matched (96.5% success rate)

**Unmatched Deaths (2)**:
- **Cause**: Deaths occurred after the last recorded telemetry window for that user/mode
- **Implication**: Final window may be incomplete; acceptable loss (<4%)

**Multiple Deaths per Window**:
- Several windows contain 2-4 deaths (cascade events)
- `deathCountInWindow` preserves count; `deathOccurredInWindow` remains binary

### Key Decision: Column Prefix Stripping

**Problem**: Raw telemetry had `metrics.` prefix (e.g., `metrics.enemiesHit`)  
**Solution**: Strip prefix to match configuration files  
**Rationale**: Enables direct lookup in `feature_roles.json` without string manipulation

```python
# Strip 'metrics.' prefix from column names
telemetry.columns = telemetry.columns.str.replace('metrics.', '')
```

### Output Schema (18 columns)

**Identifiers**: userId, modeId, timestamp  
**Combat Metrics**: enemiesHit, damageDone, timeInCombat  
**Exploration Metrics**: distanceTraveled, timeSprinting, timeOutOfCombat  
**Collection Metrics**: itemsCollected, heartsCollected, coinsCollected, pickupAttempts, timeNearInteractables  
**Derived Death Indicators**: deathOccurredInWindow (binary), deathCountInWindow (integer)

## Notebook 01: Integrity Validation

**File**: `01_integrity_check.ipynb`  
**Objective**: Verify structural, temporal, and experimental integrity before numeric processing

### Why This Notebook?

**Rationale**: Data corruption or experimental protocol violations would invalidate all downstream analysis. This notebook acts as a **quality gate** that must pass before proceeding.

### Validation Tiers

#### Tier 1: Mode Coverage Validation

**Requirement**: Every userId must appear in all modeIds

**Why?**: This is a **within-subjects design**. Each participant plays all modes to enable fair comparison. Missing modes indicate:
- Participant dropout
- Data collection failure
- Protocol violation

**Implementation**:
```python
# Detect all unique modes dynamically (supports future expansions)
unique_modes = df['modeId'].unique()
unique_users = df['userId'].unique()

# Check coverage matrix
for user in unique_users:
    user_modes = df[df['userId'] == user]['modeId'].unique()
    if set(user_modes) != set(unique_modes):
        print(f"ERROR: User {user} missing modes: {set(unique_modes) - set(user_modes)}")
```

**Result**: ✓ PASS - All 8 users have data across all 3 modes

#### Tier 2: Data Completeness

**Critical Columns**: `deathOccurredInWindow`, `deathCountInWindow`  
**Check**: No NaN values allowed in derived columns

**Why?**: These columns are derived in Notebook 00. NaNs would indicate merge failure.

**Result**: ✓ PASS - 0 NaN values detected

#### Tier 3: Plausibility Checks

**Consistency Rule**: `deathOccurred == 1` ⟺ `deathCount ≥ 1`

**Why?**: These columns are semantically linked. Inconsistency indicates logic error.

```python
inconsistent = df[
    (df['deathOccurredInWindow'] == 1) & (df['deathCountInWindow'] == 0) |
    (df['deathOccurredInWindow'] == 0) & (df['deathCountInWindow'] > 0)
]
```

**Result**: ✓ PASS - 0 inconsistencies

**Metric Validation**: All 14 numeric columns must have non-negative values

**Why?**: Negative metrics (e.g., negative damage) indicate sensor errors or data corruption

**Result**: ✓ PASS - All values ≥ 0

### Design Choice: Dynamic Discovery

**Alternative**: Hardcode expected modes (e.g., `modes = [1, 2, 3]`)  
**Chosen Approach**: Dynamically detect modes with `df['modeId'].unique()`

**Rationale**:
- Future-proof: Supports addition of Mode 4, 5, etc. without code changes
- Self-documenting: The validation report shows actual modes present
- Defensive programming: Detects unexpected mode IDs (e.g., 0, 99)

## Notebook 02: Mode Profiling

**File**: `02_mode_profiling.ipynb`  
**Objective**: Compute descriptive statistics for each metric within each mode to establish behavioral fingerprints

### Why No Normalization?

**Decision**: Analyze raw magnitude, not normalized/standardized values

**Rationale**:
1. **Absolute difficulty detection**: Mode 3's 4x death rate is meaningful in absolute terms, not relative
2. **Threshold interpretation**: Sparsity of 50% means "half the windows are zero" (interpretable)
3. **Parameter derivation**: PCG targets based on actual game values (e.g., 3.76 enemies), not z-scores

### Statistical Measures Computed

For each **(mode, metric)** pair:

| Measure | Formula | Interpretation |
|---------|---------|----------------|
| **Mean** | `Σx / n` | Average activity level |
| **Median** | 50th percentile | Robust central tendency |
| **Std Dev** | `√(Σ(x - μ)² / n)` | Volatility / stability |
| **Max** | Maximum observed | Peak intensity |
| **Sparsity %** | `(count of zeros / n) × 100` | Underutilization |

### Sparsity Analysis

**Sparsity Formula**: `(# windows with metric = 0) / (total windows for mode)`

**Why Sparsity Matters**:
- **High sparsity (80%+)**: Feature is rarely used → Mode may favor other playstyles
- **Moderate sparsity (30-60%)**: Expected for contextual features (e.g., combat doesn't occur in every window)
- **Low sparsity (0-20%)**: Feature is consistently active

**Example**: Mode 1's `enemiesHit` sparsity = 42.1%
- **Interpretation**: 58% of windows had combat engagement
- **Assessment**: Healthy combat presence without forced engagement

### Mode Health Diagnosis

**Diagnostic Criteria**:
1. **Engagement**: Mean sparsity across all metrics <50%
2. **Stability**: Standard deviation not exceeding 2× mean
3. **Balance**: No single archetype (Combat/Exploration/Collection) dominates

**Results**:

| Mode | Mean Sparsity | Mean Std Dev | Death Rate | Assessment |
|------|---------------|--------------|------------|------------|
| 1 | 48.15% | 305.09 | 0.0556/window | Good engagement, stable |
| 2 | 43.89% | 310.79 | 0.1103/window | Good engagement, stable |
| 3 | 50.31% | 335.93 | 0.2258/window | Good engagement, high lethality |

### Key Finding: Death Rate Gradient

**Observation**: Death rates form a clear gradient across modes
- Mode 1: 0.0556 deaths/window (5.6% of windows)
- Mode 2: 0.1103 deaths/window (11.0% of windows) → **2× Mode 1**
- Mode 3: 0.2258 deaths/window (22.6% of windows) → **4× Mode 1**

**Implication**: Modes represent distinct difficulty levels, not just variations

### Archetype-Specific Insights

**Combat Archetype** (5 metrics):
- Sparsity: 33-47% across modes
- Interpretation: Combat occurs in ~60% of windows (contextual feature)

**Exploration Archetype** (3 metrics):
- Low sparsity: 0-15%
- Interpretation: Movement is constant (expected in open-world game)

**Collection Archetype** (5 metrics):
- Variable sparsity: 20-70%
- Interpretation: Items are present but not always pursued

### Output

**File**: `data/processed/mode_profiles.csv`  
**Structure**: 39 rows (3 modes × 13 metrics), 6 columns (mode, metric, mean, median, std, max, sparsity)

## Notebook 03: Parameter Derivation

**File**: `03_parameter_derivation.ipynb`  
**Objective**: Select neutral baseline mode and derive initial PCG parameters

### Baseline Selection Criteria

**Goal**: Find the "Goldilocks zone" mode that is:
1. **Balanced**: Low mean sparsity (≤50% indicates active engagement)
2. **Stable**: Low mean variance (predictable, not chaotic)
3. **Safe**: Death rate >0 but low (<0.15/window target)

### Neutrality Scoring Algorithm

**Formula**:
```
NeutralityScore = (MeanSparsity × 1.0) + (DeathRate × 100.0) + (MeanStdDev × 0.1)
```

**Weight Rationale**:

| Component | Weight | Justification |
|-----------|--------|---------------|
| **Sparsity** | 1.0× | Direct engagement signal; 50% sparsity contributes 50 to score |
| **Death Rate** | 100.0× | Heavy penalty for frustration; 0.10 deaths/window contributes 10 to score |
| **Std Dev** | 0.1× | Minor stability factor; variance of 300 contributes 30 to score |

**Why These Weights?**

**Death Rate Dominance (100×)**:
- A small increase in death rate (0.05 → 0.10) adds 5 to score
- Equivalent to adding 5% sparsity or 50 units of variance
- **Rationale**: Frustration is the primary disqualifier for a neutral baseline

**Sparsity as Tiebreaker (1×)**:
- If two modes have equal death rates, lower sparsity wins
- **Rationale**: More engagement is preferable when safety is equal

**Variance as Fine-Tuner (0.1×)**:
- Only contributes 1 point per 10 units of variance
- **Rationale**: Stability is desirable but not critical for initial calibration

### Alternative Approaches Considered

#### Approach 1: Equal Weighting
```
Score = Sparsity + DeathRate + StdDev
```
**Problem**: Standard deviation (~300) would dominate sparsity (~50) and death rate (~0.10)  
**Rejected**: Disproportionate influence of variance

#### Approach 2: Z-Score Normalization
```
Score = z(Sparsity) + z(DeathRate) + z(StdDev)
```
**Problem**: Requires multiple modes for normalization; not generalizable to single-mode validation  
**Rejected**: Violates reproducibility principle

#### Approach 3: Manual Inspection
Simply pick the mode that "looks" most balanced  
**Problem**: Subjective, not reproducible, lacks academic rigor  
**Rejected**: Cannot be defended in thesis methodology

### Baseline Ranking Results

| Mode | Sparsity | Death Rate | Std Dev | **Score** | Status |
|------|----------|------------|---------|-----------|--------|
| **1** | 48.15% | 0.0556 | 305.09 | **84.21** | ✓ **BASELINE** |
| 2 | 43.89% | 0.1103 | 310.79 | **86.00** | Alternative |
| 3 | 50.31% | 0.2258 | 335.93 | **106.48** | Upper Bound |

**Mode 1 Selected**: Lowest score (84.21) indicates most neutral profile

**Why Mode 1 Beats Mode 2**:
- Mode 2 has lower sparsity (43.89% vs 48.15%) → **+4.26 to Mode 1's score**
- Mode 2 has higher death rate (0.1103 vs 0.0556) → **+5.47 to Mode 2's score**
- Death penalty (5.47) > Sparsity benefit (4.26) → Mode 1 wins

### Parameter Derivation Formula

**Target Metric = Baseline Mean × 1.2** (20% challenge margin)

**Why 20% Margin?**
- **Too conservative (1.0×)**: No challenge progression
- **Too aggressive (1.5×+)**: May overshoot acceptable difficulty
- **20% margin**: Industry standard for adaptive difficulty systems

**Example Derivations**:

| Metric | Mode 1 Mean | Target (1.2×) | Unit |
|--------|-------------|---------------|------|
| enemiesHit | 3.14 | 3.76 | enemies/window |
| damageDone | 44.86 | 53.83 | HP/window |
| timeInCombat | 5.67 | 6.80 | seconds/window |
| deathOccurred | 0.0556 | 0.067 | probability |

**All 13 Target Parameters Derived** (saved to `config/initial_parameters.json`)

### Methodological Transition Declaration

> **CALIBRATION FREEZE**: From this point forward, these parameters are **immutable**. Future telemetry will be used exclusively for **model training**, not calibration refinement.

**Why Freeze?**
1. **Prevents circular reasoning**: Training data cannot retroactively change training targets
2. **Ensures reproducibility**: Independent datasets can validate the same baseline
3. **Academic integrity**: Calibration and training phases must be temporally distinct

## Notebook 04: Survey Analysis

**File**: `04_survey_analysis.ipynb`  
**Objective**: Analyze participant questionnaire responses to establish subjective mode rankings

### Study Design

**Blind Protocol**: Modes presented as A, B, C (not 1, 2, 3)

**Why Blind?**
- Prevents numerical bias (e.g., assuming Mode 1 is "easy")
- Isolates subjective experience from expectations

**Mode Mapping**: Validated via timestamp cross-reference between survey and telemetry

### Survey Structure

#### Categorical Votes (per mode)
- "Which mode felt most balanced?"
- "Which mode was too easy?"
- "Which mode was too difficult?"
- "Which mode would you play longer?"

#### Likert Scale Ratings (per mode)
- Combat fairness: 1 (Very unfair) → 5 (Very fair)
- Exploration comfort: 1 (Too cramped) → 5 (Too open)
- Collectible availability: Categorical (Abundant → Limited) or numeric

### Data Transformation Challenges

#### Challenge 1: Inconsistent Likert Formats

**Problem**: Some responses formatted as "5 (Very fair)", others as just "5"

**Solution**: Regex parsing to extract numeric value
```python
def parse_likert(value):
    if pd.isna(value):
        return np.nan
    match = re.search(r'^(\d+)', str(value))
    return int(match.group(1)) if match else np.nan
```

#### Challenge 2: Categorical → Numeric Mapping

**Problem**: Some questions used categorical labels (e.g., "Balanced", "Frequently")

**Mapping**:
```python
category_map = {
    'Balanced': 3,          # Neutral midpoint
    'Frequently': 5,        # High frequency
    'Occasionally': 3,      # Medium frequency
    'Rarely': 1,            # Low frequency
    'Abundant': 4,          # Above neutral
    'Adequate': 3,          # Neutral
    'Limited': 2,           # Below neutral
    'Too many': 4,          # Over-abundance
    'Just right': 3,        # Perfect
    'Too few': 2            # Scarcity
}
```

**Rationale**: 5-point scale preserves ordinality; midpoint (3) = neutral perception

### Statistical Choice: Median vs Mean

**Decision**: Use **median** for Likert ratings

**Why Median?**
- **Small sample (n=7)**: Single outlier could skew mean significantly
- **Ordinal data**: Likert scales are ordinal, not truly interval
- **Robustness**: Median is less sensitive to extreme responses

**Example**:
- Ratings: [1, 3, 4, 4, 5, 5, 5]
- Mean: 3.86
- Median: 4.0

If one participant had a bad day and rated everything 1:
- Ratings: [1, 1, 3, 4, 4, 5, 5]
- Mean: 3.29 (large shift)
- Median: 4.0 (unchanged)

### Vote Aggregation

**Method**: Simple count per category per mode

**Example**: "Most Balanced" votes
- Mode 1: 4 votes
- Mode 2: 2 votes
- Mode 3: 1 vote

**Ranking**: Sort by vote count (descending)

### Results

**Subjective Rankings** (by "Most Balanced" votes):
1. Mode 1: 4/7 votes (57.1%)
2. Mode 2: 2/7 votes (28.6%)
3. Mode 3: 1/7 votes (14.3%)

**Median Ratings** (hypothetical example):
- Mode 1: Combat Fairness = 4.0, Exploration Comfort = 4.0
- Mode 2: Combat Fairness = 3.5, Exploration Comfort = 4.5
- Mode 3: Combat Fairness = 3.0, Exploration Comfort = 3.5

### Independence from Telemetry

**Critical Design Choice**: Survey analysis is performed **independently** from telemetry

**Why?**
1. **Dual validation**: Compare subjective perception to objective behavior
2. **Triangulation**: If results align, confidence increases; if divergent, investigate why
3. **Avoid confirmation bias**: Survey should not be influenced by telemetry findings

### Output

**Files**:
- `data/processed/survey_summary.csv`: Mode-level aggregated metrics
- `data/processed/survey_rankings.json`: Structured rankings with metadata

## Key Decisions & Rationale

### Decision 1: Forward Merge Direction

**Choice**: `pd.merge_asof(direction='forward')`  
**Alternative**: `direction='backward'` or `direction='nearest'`

**Rationale**:
- Telemetry timestamps mark **window end**
- Death at T=85 should map to window ending at T=100, not T=70
- Forward ensures death falls within window's observation period

**Impact**: 96.5% match rate (55/57 deaths)

---

### Decision 2: No Normalization in Mode Profiling

**Choice**: Analyze raw magnitude  
**Alternative**: Z-score standardization or min-max scaling

**Rationale**:
- Absolute values are interpretable (e.g., "3.14 enemies per window")
- Magnitude differences are meaningful (Mode 3's 4× death rate)
- Normalized values lose physical meaning

**Impact**: Parameters derived in actual game units (enemies, HP, seconds)

---

### Decision 3: Heavy Death Rate Penalty (100×)

**Choice**: Weight death rate at 100× sparsity  
**Alternative**: Equal weights or data-driven weight optimization

**Rationale**:
- Death frustration is primary disqualifier for neutral baseline
- Small death rate changes (0.05 → 0.10) should significantly impact score
- Reflects player experience research: frustration >> minor engagement drop

**Impact**: Mode 3 correctly disqualified despite acceptable sparsity

---

### Decision 4: Median over Mean for Survey

**Choice**: Use median for Likert ratings  
**Alternative**: Mean or mode

**Rationale**:
- Small sample size (n=7) vulnerable to outliers
- Ordinal data (Likert scales) better suited to median
- Robustness: Single bad response doesn't skew results

**Impact**: More stable central tendency estimates

---

### Decision 5: 20% Challenge Margin

**Choice**: Target = Baseline × 1.2  
**Alternative**: 1.1× (conservative) or 1.5× (aggressive)

**Rationale**:
- Industry standard for adaptive difficulty systems
- 1.1× too conservative (minimal progression)
- 1.5× too aggressive (risk of overshooting)
- 20% provides meaningful but manageable increase

**Impact**: Parameters provide clear but not overwhelming progression targets

---

### Decision 6: Independent Survey Analysis

**Choice**: Analyze survey without referencing telemetry  
**Alternative**: Combine datasets early

**Rationale**:
- Enables dual validation (triangulation)
- Prevents confirmation bias
- Allows discrepancy analysis if results diverge

**Impact**: Detected (potential) objective-subjective discrepancy

---

### Decision 7: Calibration Freeze

**Choice**: Lock parameters after derivation  
**Alternative**: Continuously update with new telemetry

**Rationale**:
- Prevents circular reasoning (training targets can't change during training)
- Ensures reproducibility
- Maintains temporal separation of calibration and training phases

**Impact**: Clear phase boundaries; no data contamination

## Experiments & Alternative Approaches

### Experiment 1: Death Alignment Direction

**Tested Approaches**:
1. **Forward merge** (chosen): Death → nearest following window
2. **Backward merge**: Death → nearest preceding window
3. **Nearest merge**: Death → closest window (either direction)

**Results**:
- Forward: 96.5% match rate, deaths fall within observation period
- Backward: Would assign deaths to windows that ended before death occurred (temporal violation)
- Nearest: Ambiguous for deaths at window boundaries

**Conclusion**: Forward merge respects temporal causality

---

### Experiment 2: Sparsity Definition

**Tested Approaches**:
1. **Zero-based** (chosen): Count windows where metric = 0
2. **Low-activity threshold**: Count windows where metric < 10th percentile
3. **Binary engagement**: Just track if any activity occurred

**Results**:
- Zero-based: Clear interpretation (truly inactive)
- Threshold-based: Arbitrary cutoff, mode-dependent
- Binary: Loses magnitude information

**Conclusion**: Zero-based sparsity is most interpretable

---

### Experiment 3: Neutrality Scoring Weights

**Tested Approaches**:
1. **Current** (chosen): Sparsity 1.0×, Death 100×, Std 0.1×
2. **Equal weights**: All 1.0×
3. **Z-score normalization**: Standardize before summing
4. **Manual ranking**: No formula, just inspect

**Results**:
- Current: Mode 1 clearly wins, death rate properly penalized
- Equal: Standard deviation dominates due to scale (300 >> 50 >> 0.1)
- Z-score: Requires multiple modes, not generalizable
- Manual: Not reproducible, lacks rigor

**Conclusion**: Current weights balance interpretability and empirical validity

---

### Experiment 4: Parameter Derivation Formula

**Tested Approaches**:
1. **Current** (chosen): Target = Baseline × 1.2
2. **Percentile-based**: Target = 75th percentile of baseline distribution
3. **Standard deviation**: Target = Baseline mean + 0.5 SD
4. **Fixed increment**: Target = Baseline + constant

**Results**:
- Current: Simple, scales with baseline magnitude
- Percentile: Mode-dependent, may be too conservative or aggressive
- SD-based: Assumes normal distribution (not always true)
- Fixed: Doesn't scale (0.5 enemies is big, 0.5 seconds is tiny)

**Conclusion**: Proportional scaling (1.2×) maintains relative relationships

---

### Experiment 5: Survey Aggregation Method

**Tested Approaches**:
1. **Median** (chosen): 50th percentile
2. **Mean**: Arithmetic average
3. **Mode**: Most frequent rating
4. **Trimmed mean**: Remove top/bottom 20%, then average

**Results**:
- Median: Robust to outliers, appropriate for ordinal data
- Mean: Sensitive to extremes with n=7
- Mode: May have ties or no clear winner
- Trimmed mean: Loses data with small sample

**Conclusion**: Median optimal for small-sample ordinal data
